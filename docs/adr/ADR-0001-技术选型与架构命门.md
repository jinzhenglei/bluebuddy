# ADR-0001: 采用 Electron + 自研 Agent 引擎 + OpenAI 兼容协议

- **状态**：已采纳（2026-09-26）
- **决策者**：king + AI 助手

## 背景

我们要开发一个私有化部署的桌面级智能体平台（对标腾讯 WorkBuddy），要求：
能操作本地文件、执行命令、接入多种模型、后续支持多用户与云端任务运行。
开发者为编程新手，项目同时承担教学职责。

## 决策

1. **桌面框架选 Electron**，放弃 Tauri 与纯 Web
2. **Agent 循环完全自研**（约 200 行核心代码），不用 LangChain 等编排框架
3. **模型接入统一走 OpenAI 兼容协议**（含 tool_calls），一套代码覆盖云端 API / 企业网关 / Ollama
4. **存储选 better-sqlite3**，放弃 JSON 文件
5. **架构命门**：Agent 引擎为零 Electron 依赖的纯逻辑库；文件/终端操作全部经 WorkspaceProvider 抽象

## 理由

1. Electron 的 Node 主进程天然拥有文件/进程能力，生态最成熟、新手踩坑资料多；Tauri 需 Rust，门槛与本项目"学习导向"冲突；纯 Web 无法操作本地文件，直接排除。
2. 工具调用循环的本质是"消息数组 + while + 回填结果"，是理解 Agent 原理价值最高的一层；引入重框架会导致"调库但不懂原理"，且二期服务端化时框架反而碍事。
3. OpenAI 协议是事实标准，Ollama/vLLM/各家云 API 全部兼容，避免为每个供应商写适配。
4. 会话/消息/产物是结构化查询场景（按会话取消息、按时间排序），JSON 文件在数据量增长后会失控；SQLite 单文件、零运维、天然适合私有化。
5. 这两条抽象是"任务可选本地/云端执行、产物个人/公司两级管理"终态的前提——届时同一套引擎代码进 Node 服务，只需新增 RemoteWorkspace 实现，不改工具代码。

## 放弃的替代方案

- Fork Cherry Studio 二次开发：起步快，但代码库庞大，逆向理解成本高，教学价值低
- LangChain.js / Vercel AI SDK：封装好用，但掩盖了协议细节，二期云端化受框架假设束缚
- JSON 文件存储：实现最快，查询与并发写入会在阶段 2 后成为债务

## 影响与风险

- Electron 安装包大（~80MB+）、内存占用高 → 接受，换取开发效率与生态
- 自研循环需自行处理流式 tool_calls 拼装、中断、错误回填 → 阶段 2 的重点与难点，安排充分讲解
- pnpm 12 默认阻止依赖构建脚本，需在 pnpm-workspace.yaml 维护 allowBuilds 白名单（已配置）
