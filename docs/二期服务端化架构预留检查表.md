# 二期服务端化架构预留检查表（Stage 6 / S6c）

> 目的：逐条核对"桌面版是否已为二期服务端化（多用户 / 云端任务 / 远程工作区 / 产物集中管理）预留了正确的接缝"。
> 判据不是"想法有没有"，而是"代码里那条抽象边界在不在、能不能替换"。
> 结论标记：✅ 已具备 · ⚠️ 部分具备 · ❌ 未预留（二期增量）。

## 一、两条命门（计划第一节）

| #   | 预留点                                   | 现状证据                                                                                                                                                                               | 结论 | 二期动作                                                            |
| --- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | ------------------------------------------------------------------- |
| 1   | Agent 引擎是纯逻辑库、零 Electron 依赖   | 全仓仅 `index.ts`/`ipc.ts`/`settings.ts`/`updater.ts` 四个壳层文件 `import 'electron'`；`agent/`、`tools/`、`workspace/`、`skills/`、`llm/`、`db/`、`permissions/`、`mcp/` 均无        | ✅   | 服务端直接 `import { runAgentTurn }` 即可复用                       |
| 2   | 引擎"可被 Node 直接 import 跑通一次任务" | `src/main/agent/engine-headless.spec.ts` 在**普通 Node 进程**（断言 `process.versions.electron` 为 `undefined`）里，用脚本化假 LLM 驱动 `write_file` 真实落盘并产出 artifact，测试通过 | ✅   | 已自动化验证，纳入 test 门禁防回归                                  |
| 3   | 文件/终端操作走 WorkspaceProvider 抽象   | `workspace/provider.ts` 定义接口（readFile/writeFile/listDir/exec/resolve），`local.ts` 是唯一实现；内置工具只经 `ctx.workspace`，不碰 `node:fs`/`child_process`                       | ✅   | 新增 `RemoteWorkspace implements WorkspaceProvider`，工具代码零改动 |

## 二、依赖注入边界（引擎对外零反向依赖）

| #   | 预留点         | 现状证据                                                                                                      | 结论 |
| --- | -------------- | ------------------------------------------------------------------------------------------------------------- | ---- |
| 4   | LLM 调用可替换 | `RunAgentTurnOptions.llmCall: LlmCallFn`，生产传 `streamChat` 封装、测试传 mock（见 headless 用例）           | ✅   |
| 5   | 工具执行可替换 | `registry: ToolRegistry` + `toolCtx: ToolContext` 由入参注入；MCP 工具与内置工具同经 `registry.register` 汇入 | ✅   |

## 三、进程隔离与数据模型

| #   | 预留点                             | 现状证据                                                                                                                                                  | 结论 |
| --- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| 9   | 渲染进程能力白名单隔离             | `preload/index.ts` 经 `contextBridge` 只暴露 `api.*` 白名单，`sandbox:false` 但 `contextIsolation` 开、无 `nodeIntegration`；fs/shell 只能走指定 IPC 信道 | ✅   |

## 四、明确未预留项（二期增量，届时按 user_version 迁移）

| #   | 计划提及的预留位                                     | 现状   | 结论 | 影响与成本                                               |
| --- | ---------------------------------------------------- | ------ | ---- | -------------------------------------------------------- |
| 13  | `artifacts` 表 `remote_uri` 字段（产物云端两级管理） | 未加列 | ❌   | 二期 `ALTER TABLE` + `user_version` 迁移即可，低风险     |
| 14  | `tasks` 视图 / 任务队列（本地+云端多任务）           | 未建   | ❌   | 二期新增表/视图；现有 sessions/messages 可作本地任务基座 |
| 15  | 多用户 / 账号体系 / 模型网关                         | 未做   | ❌   | 属计划已声明的"首期不做"边界，非遗漏                     |

## 五、总体结论

- **命门①达成且可自动化验证**：引擎确为纯逻辑库，能在无 Electron 的 Node 里跑通一次任务（headless 用例已进 test 门禁）。
- **可替换边界清晰**：LLM、工具、工作区、事件流、批准、存储六条接缝全部依赖注入，二期服务端化主要是"换实现 + 加表列"，不需要动引擎内核与工具代码。
- **两项数据位（remote_uri / tasks）与账号体系未预留**：均为二期增量，走既有 `user_version` 迁移路径，成本可控，不构成分层缺陷。

> 复核方式：`grep -R "from 'electron'" src/main` 应只见 4 个壳层文件；`vitest run src/main/agent/engine-headless.spec.ts` 应通过。
